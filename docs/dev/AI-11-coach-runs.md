# AI-11 · 미션 편성 그래프 · `/v1/coach/runs`

계약은 `../03` §5·§8, 노드는 `../01` §3.1.

> ⚠ **이 갈래는 백엔드 스키마 합의 없이 끝나지 않는다.**
> `../03` §11 ① 이 "①이 가장 급하다"고 한 것이 현실이 됐다 — `missions` 실제 컬럼에
> 우리 `proposal` 이 들어가지 않는다
> ([AI-13](AI-13-backend-contract-reconciliation.md) §3.1·§3.2).
> `assess`·`retrieve`·`compose` 는 먼저 만들 수 있고, 막히는 것은 **반환 모양과
> 저장**이다.

**LangGraph 그래프는 하나다.** 노드 넷의 이름이 곧 계약의 `steps[].name` 이라,
**이름을 바꾸면 계약이 바뀐다.**

---

## 1. 노드 넷

| 노드 | 하는 일 | 실패 시 |
|---|---|---|
| `assess` | [AI-4](AI-4-assessment-endpoint.md) 의 계산을 그대로 부른다 | 입력 수준 강등, 계속 |
| `retrieve` | [AI-8](AI-8-vector-index.md) 검색 | `video: null` 로 계속 |
| `compose` | 세션 편성 + 문장 생성 (**LLM 1회**) | 규칙 편성으로 강등 |
| `verify` | 인용·금지어휘·연령 일치 | **거부.** 여기서만 전체 실패 |

**LLM 호출은 `compose` 한 곳뿐이다** (`../01` §3.1). 비용·지연·실패가 한 곳에 모여야
관측과 강등이 쉽다.

**`assess` 는 `/fitness/assessment` 와 같은 함수를 부른다.** 두 벌이 되면 같은
사람이 화면과 미션에서 다른 요인을 대상으로 받는다.

**체크포인터를 붙이지 않는다** (`../01` §3.1). LangGraph 상태는 요청 수명 동안만
살고, 영속 상태의 정본은 `coach_runs` 테이블이다.

## 2. 강등과 거부는 다르다

| 상황 | 동작 | `steps[].status` |
|---|---|---|
| 영상이 없다 | `video: null` 로 계속 | `partial` |
| LLM 실패 | 처방 어휘 기반 **규칙 편성**으로 계속 (인용 유지) | `partial` |
| **인용 0** | **거부.** `proposal` 은 `null` | `failed` |

**규칙 편성 경로가 실제로 돌아야 한다.** LLM 장애 때만 쓰는 코드는 장애 때 처음
실행되고 그때 실패한다. `compose` 를 강제로 규칙 편성으로 돌리는 검사를 둔다.

**강등 비율이 5%를 넘으면 LLM 장애 신호다** (`../01` §5).

`verify` 는 넷을 검사한다 — 인용 ≥ 1, 본문 `[n]` 이 범위 안, 금지 어휘 없음, 세션
연령대가 프로필과 일치. **부분 통과는 없다** (`../03` §5.4).

## 3. 비동기와 중복

| | |
|---|---|
| `POST` | `202` · `run_id` · `poll_after_ms` |
| `GET` | `200` · `status` · `steps` · `proposal` |
| 소요 | 예상 15~40초 |
| 중복 | 같은 프로필에 실행 중인 run이 있으면 `409 RUN_IN_PROGRESS` |

**버튼을 두 번 눌러 제안이 두 개 생기면 어느 것을 승인했는지가 흐려진다**
(`../03` §5).

**run 상태를 어디에 두는지가 §6 ①이다.** AI 서비스는 서비스 테이블에 쓰지 않으므로
(`../03` §1) `coach_runs` 에 못 쓴다. 태스크 2개가 AZ 분산이라 프로세스 메모리에
두면 폴링이 다른 태스크로 가서 `404` 가 난다.

## 4. 승인 게이트 — AI 쪽이 보장할 것

`../03` §8 의 넷 중 AI가 지키는 것은 셋이다.

- **`missions` 쓰기 경로가 존재하지 않는다.** 코드에 없어야 한다
- 승인 이전에 부작용 있는 도구가 호출되지 않는다
- 모든 제안에 근거 인용이 남는다

**AI에 미션을 만들 경로가 없다** — 이것이 승인 게이트의 근거다 (`../03` §1).

`proposal.missions[]` 는 `missions` 테이블 행 모양으로 설계됐다. **실제 컬럼이
다르면 매핑 코드가 승인 트랜잭션 안에 생기고 "복사만 한다"는 원칙이 깨진다**
(`../03` §11 ①).

**다르다.** 확인된 차이는 다섯이다
([AI-13](AI-13-backend-contract-reconciliation.md) §3.1).

| 우리가 내는 것 | 저장될 자리 |
|---|---|
| `sessions[]` (요일·운동명·요인·분·영상·근거) | **없다.** 제안 1건 = 1행, `video_id` 단수 |
| `copy.child` · `copy.parent` | `description` 하나 — 아이/부모 분리가 사라진다 |
| `participants[].role` | `mission_participants` 에 role 컬럼 없음 |
| `evidence[]` · `citations[]` | `rationale varchar(400)` — **인용이 저장되지 않는다** |
| `fitness_factor` · `duration_min` | `target_metric`(STEPS/TIME) · `target_value` |

**인용이 가장 급하다.** `../01` §5 는 인용률을 임계가 아니라 **절대값 100%** 로
두었다. `rationale` 은 자유 텍스트라 어느 문서에서 나왔는지 대응이 없다 —
검증할 수 없는 것은 인용이 아니다. `coach_message_citations` 가 대화 쪽에 이미
있으니 **미션 쪽에 같은 모양이 필요하다.**

### 4.1 run의 단위가 다르다

| | 우리 (`../03` §5) | 백엔드 |
|---|---|---|
| 단위 | 프로필 (`409` 도 프로필 기준) | **가족·주차** (`uq_coach_run (family_id, week_start)`) |
| 트리거 | 사용자가 "이번 주 미션 받기" | **일요일 20시 CRON** + MANUAL |
| `status` | `running`·`succeeded`·`failed`·`refused` | `RUNNING`·`APPROVED`·`REJECTED` |

**백엔드 쪽 단위가 맞다.** 편성 입력이 `profile_refs[]` 1~4명이니 실제 단위는
가족이다. `../03` §5 의 409 문구를 가족·주차 기준으로 고쳐야 한다.

**`REJECTED` 와 우리 `refused` 는 다르다.** 앞은 보호자가 거절한 것이고 뒤는 AI가
근거를 못 찾은 것이다. 한 값에 넣으면 거부율이 "보호자가 싫어한 비율"과 섞인다.

## 5. 검사

| 무엇 |
|---|
| 코드 전체에 `missions` INSERT 경로가 없다 |
| LLM을 실패시키면 규칙 편성으로 `succeeded` 가 나온다 |
| 인용 0이면 `refused` 이고 `proposal` 이 `null` |
| `steps[].name` 이 `assess`·`retrieve`·`compose`·`verify` 다 |
| 같은 프로필 두 번째 `POST` 가 `409` |
| 아이 세션에 성인 연령대 자료가 섞이면 `verify` 가 막는다 |
| `응원` 역할이 편성 대상에서 빠진다 (`../03` §5.1) |
